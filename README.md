# Self-Adapting-Phishing-Detector-MLOps-Pipeline
Self-adapting phishing detection pipeline using MLOps industry practices, active learning, drift detection, human feedback, automated retraining and gated deployment.

## Problem Statement

A small business operates a custom email system used by its employees for day-to-day communication. As the organisation grows, manually inspecting suspicious emails is no longer practical, so it needs an automated phishing detection service that can analyse the raw content of incoming emails and decide whether each message should be allowed, blocked, or sent to a human reviewer.

Phishing attacks are not static. Attackers regularly change their language, formatting, social-engineering techniques, and campaign patterns to avoid existing detection systems. A model that performs well when it is first deployed may therefore become less effective over time as the emails it receives begin to differ from the data on which it was trained. Requiring an engineer to continually notice these changes, collect examples, retrain the model, evaluate it, and redeploy it manually would make the system difficult to maintain.

The business therefore needs the detector to operate as a continuously monitored system rather than as a one-time machine-learning model. For every incoming email, the system should produce a phishing score and use a decision policy to determine whether the message can be confidently allowed or blocked. Emails for which the system is sufficiently uncertain should instead be placed into a review queue so that a human can provide the correct label.

Human review capacity is limited. Under normal operation, no more than **5% of incoming emails** should require manual review. The review queue should therefore prioritise emails whose labels are expected to be most useful for improving the detector rather than simply requesting labels for large numbers of randomly selected messages.

Incorrectly blocking legitimate business email could interrupt normal operations, so the system must keep the **false-positive rate at or below 1%** on production-representative traffic. Within that constraint, it should detect as many phishing emails as possible. The score at which an email is blocked must not be chosen as an arbitrary constant; it should be fitted from evaluation data so that the permitted false-positive rate is respected. The boundary used for human review should likewise be derived from the available review capacity. Because different model versions may produce different score distributions, these decision thresholds need to be recalculated whenever a new model is trained.

The service must also be suitable for use as part of an interactive email system. Processing a single email should have a **p95 latency below 500 ms on the declared deployment hardware**, so that phishing detection does not introduce unreasonable delays into email handling.

Once deployed, the system should monitor its predictions and incoming email patterns for signs that its behaviour or the underlying data distribution is changing. This includes performance degradation where labelled evidence is available, broader distribution drift, and groups of similar low-confidence emails that may indicate the beginning of a previously unseen phishing campaign.

When sufficient new human labels become available, model performance deteriorates, significant drift is detected, or a new campaign is identified, the system should be capable of initiating a retraining workflow. Human involvement should be concentrated on supplying ground-truth labels for selected emails; detecting changes, starting retraining, evaluating the resulting model, and managing deployment should otherwise be automated.

Retraining alone must not be considered sufficient reason to replace the production model. Every candidate must first be evaluated against the same operational constraints as the existing system. A new model and its associated decision thresholds may only progress towards production if the false-positive, review-capacity, and latency constraints remain satisfied, performance on novel phishing campaigns does not regress, and the candidate improves at least one declared objective. Deployment should use a controlled canary release so that an unsuitable candidate can be rejected or rolled back rather than immediately replacing the working production system.

Every production prediction should be traceable to the model and decision policy that produced it, and trained models should retain lineage to the data and evaluation results from which they were created. The model and its fitted decision thresholds should therefore be treated as a single versioned production artifact.

A key test of the completed system is how efficiently it responds to a phishing campaign containing patterns the current model has not previously learned. After the system detects the new behaviour, a human reviewer should only need to label a relatively small, intelligently selected set of examples before the pipeline can retrain and recover strong detection of the campaign without exceeding the **1% false-positive** or **5% review** limits. The project should measure how many labels this recovery requires and compare the result with random sampling, demonstrating whether active learning reduces the amount of human effort needed to keep the detector current.
